# Caddy public ingress provisioning

This runbook describes the Linux host boundary for public D Hosting traffic. It is an operator procedure, not proof that a production host has already passed acceptance.

## Required topology

- Use a dedicated Linux runtime host with rootless Podman and cgroup v2.
- Put Caddy and customer runtime containers on the same private Podman network, `dsquare-private`.
- Customer runtime containers listen only on their private network alias at port 3000. Never publish customer container ports on the host.
- Caddy is the only public HTTP entry point. Publish TCP 80 and TCP 443; publish UDP 443 if HTTP/3 is enabled by the selected Caddy build.
- Publish Caddy's admin port only on host loopback: `127.0.0.1:2019:2019`. Never expose port 2019 to the public network or customer containers.
- Persist Caddy's `/data` and `/config` directories in named volumes so ACME account state and certificates survive container replacement.

## Provisioning outline

Run as the dedicated runtime service account, not as root:

```sh
podman network create dsquare-private
podman volume create dsquare-caddy-data
podman volume create dsquare-caddy-config
```

Use the pinned Caddy image `docker.io/library/caddy:2.11.8` or a later reviewed patch release. Start Caddy on the private network with the following host port bindings and persistent volumes. The Caddy process inside the container must listen on `0.0.0.0:2019`; the host mapping is what restricts access to loopback.

```sh
podman run -d \
  --name dsquare-caddy \
  --network dsquare-private \
  --restart=unless-stopped \
  -p 80:80/tcp \
  -p 443:443/tcp \
  -p 443:443/udp \
  -p 127.0.0.1:2019:2019/tcp \
  -v dsquare-caddy-data:/data \
  -v dsquare-caddy-config:/config \
  docker.io/library/caddy:2.11.8
```

If the image entrypoint requires an initial config file in the chosen deployment environment, provide a minimal bootstrap config and ensure the runtime agent replaces it only through the loopback `POST /load` API. Do not disable the admin endpoint's origin protections or publish it beyond loopback.

Configure the runtime agent with:

- `RUNTIME_AGENT_CADDY_ADMIN_URL=http://127.0.0.1:2019/`
- `RUNTIME_AGENT_PODMAN_NETWORK=dsquare-private`
- A private Podman socket path and persistent runtime workspace settings as described in the runtime agent README.

The Caddy and runtime containers must resolve each other's private network aliases. The runtime agent's Caddy admin URL is a host-loopback address and must not be reused by customer workloads.

## DNS and HTTPS

1. Point each verified website hostname's public DNS A/AAAA records to the ingress host.
2. Ensure public inbound TCP 80 and 443 reach the Caddy container. If HTTP/3 is enabled, allow UDP 443 too.
3. Keep Caddy's data/config volumes persistent and writable only by the service account.
4. Configure the TLS contact email if required by operations policy.
5. The generated Caddy JSON config obtains certificates through ACME for verified hostnames and explicitly sends HTTP requests to HTTPS with a 308 redirect.
6. Do not activate a hostname until DNS points to this ingress host and the domain ownership verification has passed.

Caddy v2.11.8 or newer is required for the request-body and HTTP idle-timeout settings generated by the controller.

## Public request controls

The generated per-host route:

- redirects HTTP to HTTPS;
- limits request bodies to 10 MiB;
- bounds total upload time, stalled uploads, request-header time and header size;
- uses low-latency reverse-proxy flushing for streaming responses;
- supports WebSocket upgrades through Caddy's native reverse proxy;
- permits a stream to remain open for up to 24 hours and delays closure during config reloads;
- bounds upstream connection and response-header establishment time;
- returns a generic, non-cacheable 503 page for proxy gateway errors without exposing private upstream details.

Application-generated response statuses such as 404 and 500 are not rewritten by the gateway error handler.

## Acceptance checklist (must pass before customer execution)

- [ ] Confirm `podman network inspect dsquare-private` shows Caddy and runtime workloads attached to the intended private network.
- [ ] Confirm the host listens on public TCP 80/443 and, if enabled, UDP 443.
- [ ] Confirm `127.0.0.1:2019` responds locally and is unreachable from another host on the public network.
- [ ] Confirm Caddy data/config volumes survive container restart and replacement.
- [ ] Verify a verified hostname receives a valid ACME certificate and HTTP returns a 308 HTTPS redirect.
- [ ] Verify unknown/unverified hostnames do not route to a customer runtime.
- [ ] Verify request bodies larger than 10 MiB receive 413, including chunked requests without Content-Length.
- [ ] Verify normal uploads complete within configured limits and stalled uploads are terminated.
- [ ] Verify Server-Sent Events and chunked streaming are delivered without proxy buffering delays.
- [ ] Verify WebSocket handshake and bidirectional frames work, including a connection across a Caddy config reload.
- [ ] Stop a test runtime and verify users receive the generic 503 response without internal addresses or stack traces.
- [ ] Verify normal application 404/500 responses remain unchanged.
- [ ] Run the builder/runtime isolation, deployment activation, rollback, restart and recovery acceptance suites.
- [ ] Keep `executionEnabled: false` until every required acceptance check is recorded as passing.

No customer execution is authorized by completing this document alone.
